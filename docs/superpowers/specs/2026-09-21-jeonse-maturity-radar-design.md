# 전세 만기·역전세 레이더 설계

## 개요

국토교통부 실거래가 공공데이터를 활용하여 **아파트 단지별 전세 만기 도래 물량과 역전세 규모를 예측**하고,
부수적으로 **매매 신고가의 등기·해제 여부를 검증**하여 공개하는 서비스.

무료 공개 페이지로 검색 유입을 만들고, 만기 알림과 리드 목록을 유료화하는 것이 수익 모델이다.

## 배경과 전제

이 설계를 규정하는 네 가지 전제. 이후 모든 결정이 여기서 파생된다.

| 전제 | 내용 | 설계에 미치는 영향 |
|------|------|-------------------|
| 목적 | 수익화 사이드 프로젝트 | 데이터 신선도·차별점·경쟁 서비스 유무가 최우선 판단 기준 |
| 과금 대상 | B2B 부동산 업계 (중개업소·투자자) | 개별 물건이 아닌 단지 단위 집계가 오히려 적합 |
| 판로 | **업계 접점 없음 → 인바운드(검색)만** | 콘텐츠를 페이월 뒤에 숨길 수 없음. SEO가 유일한 생명선 |
| 리소스 | 주 5~10시간, 첫 공개 2~3개월 (총 60~100시간) | 결제·계정·앱·지도 전부 1차 범위 밖 |

### 법적 전제 (중요)

기존 `funapp`은 네이버 부동산 내부 API를 크롤링한다. **이 데이터는 유료 서비스에 재판매할 수 없다**
(네이버 이용약관 위반 및 데이터베이스권 침해 소지). 반면 국토교통부 실거래가 공공데이터는
공공데이터포털 기준 **"이용허락범위 제한 없음"** 으로 상업적 이용이 자유롭다.

따라서 **이 서비스는 공공데이터만으로 100% 성립해야 하며, 네이버 데이터를 일절 포함하지 않는다.**
이것이 funapp을 확장하지 않고 별도 프로젝트로 분리하는 근본 이유다. 크롤러가 같은 배포물 안에
있으면 그 법적 리스크가 유료 서비스에 그대로 전이된다.

### funapp에서 가져오는 것

데이터가 아니라 **코드 패턴**만 이식한다.

- `WatchRegion` — 관심 지역 관리 구조
- `NotificationService` + `EmailNotifier` — 알림 파이프라인
- `@Scheduled` 배치 구조 (`CrawlScheduler`)
- `CrawlServiceTest` — 테스트 작성 패턴

**의도적으로 다르게 가는 부분:**

| 항목 | funapp | 본 서비스 | 이유 |
|------|--------|-----------|------|
| 금액 표현 | `String` (`Article.currentPrice`) | `BIGINT` (원 단위) | 금액 연산이 코어. 문자열로는 불가 |
| 면적 | `Double` | `DECIMAL(10,2)` | 버킷 산출 시 부동소수 오차 회피 |
| 수집 주기 | 30분 | 1일 1회 | 실거래 신고는 일 단위 갱신 |
| 알림 주기 | 즉시 | 주 1회 다이제스트 | 월 단위 지표. 건건이 보내면 스팸 |
| 수집 실패 | 로그만 남기고 진행 | **재시도 큐에 잔존** | 백필에 구멍이 생기면 지표가 틀림 |

### 아파트 전월세 실거래가 자료 (15126474)

핵심 데이터 소스. 조회 파라미터는 `LAWD_CD`(법정동 시군구 5자리) + `DEAL_YMD`(계약년월 6자리).

제공 항목 중 본 서비스가 사용하는 것:

- 보증금액, 월세금액, 전용면적, 층, 계약년/월/일
- **계약기간** — 만기월 산출의 근거

- 지역코드, 법정동, 지번, 아파트명, 건축년도

개인정보 보호로 **동/호 정보는 제공되지 않는다.** 이 제약이 지표 설계 전체를 규정한다(아래 참조).

## 1. 수집 파이프라인

### 1.1 호출 단위와 백필 규모

API 1회 호출 = `(시군구코드, 계약년월)` 한 쌍. 전국 시군구는 약 250개.

| 대상 | 기간 | 호출 수 |
|------|------|--------|
| 전월세 | 36개월 (역전세 계산에 과거 2~3년 필요) | 250 × 36 = 9,000 |
| 매매 | 24개월 (시세 비교용) | 250 × 24 = 6,000 |
| **합계** | | **15,000** |

일 쿼터 10,000건이므로 **전국 백필은 이틀이면 완료된다.** 크롤링과 달리 차단 위험이 없다.

응답은 `numOfRows`/`pageNo`로 페이징한다. 거래량이 많은 시군구는 한 달에 수천 건이 나오므로
`numOfRows=1000`으로 전 페이지를 순회한다.

### 1.2 증분 수집 — 직전 3개월 재수집

두 가지 이유로 "한 번 넣고 끝"이 불가능하다.

1. 실거래 신고 기한이 계약일로부터 30일이라, 지난달 거래가 이번 달에 추가로 들어온다.
2. **`해제여부`와 `등기일자`는 나중에 값이 바뀌는 필드다.**

따라서 매일 **당월 포함 직전 3개월**을 전국 재수집(upsert)한다.

```
일일 증분 = 250개 시군구 × 3개월 × 2 API = 1,500 호출/일
```

쿼터 10,000건 대비 충분한 여유가 있다.

### 1.3 거래 식별 — deal_hash

**API는 거래 고유 ID를 제공하지 않는다.** 자연키 해시를 직접 만든다.

```
deal_hash = SHA256(지역코드|법정동|지번|전용면적|층|계약년|계약월|계약일|금액필드)

  매매   금액필드 = 거래금액
  전월세 금액필드 = 보증금액|월세금액
```

**해시에 `해제여부`, `등기일자`를 포함해서는 안 된다.** 이 값들은 나중에 변하므로, 해시에 넣으면
값이 바뀔 때마다 새 행이 생겨 같은 거래가 중복된다. 해시는 불변 필드로만 만들고,
`INSERT ... ON DUPLICATE KEY UPDATE`로 가변 필드만 덮어쓴다.

알려진 한계: 같은 날·같은 단지·같은 면적·같은 층·같은 금액 거래가 2건이면 1건으로 합쳐진다.
발생 빈도가 극히 낮아 허용한다.

### 1.4 단지 식별 정규화 — aptSeq 기준

매매 API와 전월세 API의 아파트명 표기가 서로 흔들린다
("래미안OO" / "래미안 OO" / "OO아파트(1단지)"). **이름으로 조인하면 같은 단지가 갈라진다.**

두 API 모두 **`aptSeq`(단지 일련번호, 예 `11110-2519`)** 를 제공한다.
**`(지역코드, aptSeq)`를 UNIQUE 키**로 `complex` 마스터를 구성한다.

2026-09-21 실측(6개 시군구 × 4개월, 전월세 17,532건)으로 확인한 근거:

| 항목 | 결과 |
|------|------|
| `aptSeq` 채움률 | **100%** (매매·전월세 양쪽) |
| 고유 aptSeq / 고유 (시군구,법정동,지번) | 1,364 / 1,315 |
| 한 지번에 서로 다른 aptSeq가 2개 이상 | **43건** — 지번으로 묶으면 다른 단지가 합쳐진다 |
| 한 aptSeq가 여러 지번에 걸침 | **0건** |
| 한 aptSeq에 서로 다른 아파트명 | **0건** |

지번 기준은 서로 다른 단지 43쌍을 하나로 합친다(예: 강남구 개포동 12 → `11680-279`, `11680-280`).
aptSeq 기준은 그 오류가 없고, **한 aptSeq 안에서 아파트명 흔들림이 0건**이라 최빈값 수렴 로직도
필요 없다. 표시용 단지명은 해당 aptSeq에 등장한 이름을 그대로 쓴다.

법정동·지번은 식별 키가 아니라 **표시·검색용 속성**으로 보존한다.
수동 병합 테이블은 만들지 않는다 — 병합이 필요한 사례가 관측되지 않았다.

### 1.5 면적 버킷

전용면적이 84.97 / 84.9 / 84.99처럼 흩어져 그대로는 시세 비교가 불가능하다.
**1㎡ 단위 반올림**으로 `area_bucket`(INT)을 만들고, 시세는 버킷 내 **중위값**을 사용한다.

### 1.6 에러 처리

공공 API는 **에러도 HTTP 200으로 반환하고 body의 `resultCode`로 구분한다.**
파서가 반드시 이 코드를 판정해야 하며, `RestClient`의 상태 코드만 보면 전부 성공으로 처리된다.

| resultCode | 상황 | 처리 |
|-----------|------|------|
| `00` | 정상 | SUCCESS, 행 수 기록 |
| `03` | NODATA | **SUCCESS(0건). 재시도하지 않는다** |
| `22` | 쿼터 초과 | **당일 배치 전체 즉시 중단.** 미처리분은 PENDING 유지 |
| `30` | 인증키 미등록 | 즉시 중단 + 운영자 알림. 재시도 무의미 |
| 기타 / 네트워크 / 5xx / XML 파싱 실패 | 일시 장애 | 지수 백오프 3회 → FAILED, 익일 배치가 재시도 |

**`03`(NODATA)을 실패로 처리하면 안 된다.** 거래가 없는 군 지역은 0건이 정상이며,
실패로 기록하면 재시도 큐에 영원히 비워지지 않는 항목이 수천 건 쌓인다.

**`22`(쿼터 초과)는 재시도하면 안 된다.** 계속 호출하면 상황이 악화될 뿐이다.

### 1.7 멱등성

배치는 중간에 죽는다는 전제로 설계한다.

- 수집: `deal_hash` UNIQUE + upsert가 멱등성을 보장한다. 어디서 죽든 재실행하면 이어진다.
- `ingest_log`: `(api_type, region_code, deal_ym)` UNIQUE로 상태만 갱신한다.
- 집계: 원본에서 전량 재계산이므로 그냥 다시 돌리면 된다.

**집계 중간 상태가 화면에 노출되어서는 안 된다.** 집계 테이블에 `snapshot_date`를 두고
**조회는 완료된 최신 스냅샷만** 참조한다. 새 스냅샷 빌드가 실패해도 직전 스냅샷이 계속 서비스된다.

## 3. 지표 산식

### 3.1 설계를 규정하는 한계 (반드시 유지)

전월세 API는 개인정보 보호로 **동/호를 제공하지 않는다.** 따라서 특정 물건의 전세 계약이
현재도 유효한지를 추적하는 것은 **원리적으로 불가능하다.** 갱신되면 새 계약이 들어오지만
같은 집인지 식별할 방법이 없다.

**그러므로 모든 지표는 개별 물건이 아니라 단지×평형 집계 단위로 정의한다.**
"이 집이 역전세다"라는 표현은 만들지 않으며, 만들면 틀린다.

```
OO아파트 84㎡ — 2026년 12월 만기 도래 추정 14건,
당시 보증금 중위 5.2억, 현재 전세 시세 4.4억 → 세대당 평균 8,000만원 차액
```

이 입도는 타겟과 일치한다. 중개사는 특정 집이 아니라 "이 단지에서 몇 건이 언제 나오는가"를 필요로 한다.

### 3.2 만기월 산출

`계약기간` 필드의 **실제 형식은 `YY.MM~YY.MM`** 이다 (예: `25.05~27.05`).
2026-09-21 실측(18,287건) 형식 분포:

| 형식 | 비율 | 처리 |
|------|------|------|
| `YY.MM~YY.MM` | 73.6% | 종료월을 만기월로 사용 |
| 공백 | 26.0% | 계약일 + 24개월 추정 |
| `~YY.MM` (시작 없이 종료만) | 0.4% | **종료월은 유효하므로 그대로 사용** |
| `YYYYMM~YYYYMM` | **0%** | 존재하지 않는 형식 |

공백 26%는 표본에 2021년치를 포함한 결과다. 백필 대상 구간(최근 36개월)만 보면
채움률은 **95%+** 이며, 스펙 §6의 50% 게이트를 통과한다.

2자리 연도는 `2000 + yy`로 해석한다 (실측 분포: 21~27).

1. `계약기간`에서 종료월이 파싱되면 **그 달을 만기월**로 사용한다 (시작월 결측은 무방).
2. 종료월을 얻지 못하면 **계약일 + 24개월**로 추정하고 `term_estimated = true`를 기록한다.

추정치는 화면에서 확정치와 구분해 표기한다. 추정을 확정인 것처럼 보이면 한 번 틀렸을 때
서비스 전체의 신뢰가 사라진다.

### 3.3 대상 필터 — 순수 전세만

**`monthly_rent = 0`인 계약만** 사용한다. 반전세를 보증금만으로 비교하면 왜곡된다.

### 3.4 역전세 갭

```
median_deposit_then     = 만기월이 m인 계약들의 보증금 중위값
                          (해당 단지·평형, monthly_rent = 0)
current_median_deposit  = 최근 6개월 전세 실거래 보증금 중위값 (§3.5의 폴백 적용)

gap_amount = median_deposit_then − current_median_deposit     (양수 = 역전세)
gap_rate   = gap_amount / median_deposit_then
```

`median_deposit_then`은 과거 실제 체결가이므로 **폴백이 필요 없다** — 남의 단지 시세를
빌려올 일이 없다. 그러나 폴백이 필요 없다는 것과 믿을 만하다는 것은 다르다. 만기월의
계약이 1건이면 `median_deposit_then`은 중위값이 아니라 그 한 건의 가격이고, 갭의 오차는
그쪽이 지배한다.

따라서 **`confidence`는 양쪽 중 낮은 쪽으로 정한다**:

```
confidence = min( current_median_deposit 의 confidence,   # §3.5의 폴백 계단
                  contract_count 의 표본 등급 )            # §3.5의 등급표 그대로
```

§3.5의 "레벨과 표본 수 중 낮은 쪽을 채택한다"를 then 쪽에도 똑같이 적용하는 것이며,
같은 절의 "표본 부족을 숨기지 않는다"가 요구하는 바이기도 하다.

> **개정 이력.** 최초 스펙은 "폴백은 current_median_deposit에만 적용되며, 그 결과가
> 해당 행의 confidence를 결정한다"고 했다. 2026-09-22 전국 부분 데이터(만기 예측
> 470,663행)로 실측한 결과 57.8%가 계약 1건이었고, 갭 상위 50위 중 44개가 1건짜리였다.
> 마곡엠밸리2단지 115㎡는 계약 1건·갭 6.78억에 HIGH가 붙었다. 1건 그룹의 최대 갭은
> 35억, 5건 이상 그룹은 9억 — 극단값이 시장이 아니라 표본 빈약의 산물이었다.
> 원장 F-41.

### 3.5 표본 부족 처리 — confidence 폴백 계단

최근 6개월에 해당 단지·평형 거래가 0건이면 계산이 불가능하다. 단계적으로 폴백한다.

| 레벨 | 산출 범위 | confidence 상한 |
|------|----------|----------------|
| L1 | 단지 + 평형, 최근 6개월 | HIGH |
| L2 | 단지 전체 평형, ㎡당 단가 환산 | MEDIUM |
| L3 | 법정동 + 평형 | LOW |

각 레벨 내 표본 수 기준: `10건 이상 = HIGH`, `3~9건 = MEDIUM`, `1~2건 = LOW`, `0건 = 다음 레벨로`.
레벨과 표본 수 중 **낮은 쪽**을 최종 confidence로 채택한다.

**표본 부족을 숨기지 않는다.** 화면에 "거래 2건 기준"처럼 그대로 노출한다.

### 3.6 갱신권 소진 — 유료화의 핵심 지표

`renewal_right_used = true`인 계약은 이미 갱신요구권을 사용했으므로
**다음 만기에는 갱신권이 없다.** 5% 인상 제한으로 버틸 수 없어 실제로 시장에 나올 확률이
현저히 높다.

`useRRRight` 필드는 **`"사용"` 또는 공백 두 값만 존재한다** — `"미사용"`이라는 값은 오지 않는다.
따라서 `공백 = 미사용`으로 해석한다. 2026-09-21 실측(17,532건):

| 구분 | 비율 |
|------|------|
| 전체 중 `useRRRight = 사용` | **18.2%** |
| `contractType = 갱신` | 36.1% |
| 갱신 계약 중 `사용` | **50.3%** (나머지 49.7%는 합의갱신) |

전체 전월세의 18%가 갱신권 소진분이라는 뜻이며, 단지 단위로 보면 충분히 유의미한 모수다.

따라서 만기 물량을 두 층으로 나눠 제공한다.

```
12월 만기 14건 중 갱신권 소진 9건
```

앞의 14건은 통계이고, **뒤의 9건은 영업 리드다.** 이 구분이 유료 전환의 핵심 근거이며,
현재 시장의 주요 서비스가 제공하지 않는 지표다.

`maturity_forecast.renewal_exhausted_count`로 저장한다.

### 3.7 신고가 검증 — 점수화하지 않는다

**신뢰도 점수를 만들지 않는다.** 임의 가중치로 산출한 "신뢰도 62점"은 근거가 없고,
특정 거래를 낙인찍는 행위가 되어 법적 위험을 만든다. **사실만 나열한다.**

```
최고가 12.5억 (2026-03-14 계약) — 계약 후 191일 경과, 등기 미확인, 직거래
```

플래그 판정 규칙:

| flag_type | 조건 |
|-----------|------|
| CANCELED | `cancel_yn = 'O'` |
| UNREGISTERED | `registered_date IS NULL` **AND** `계약일 + 60일 < 오늘` **AND** `cancel_yn != 'O'` |
| DIRECT | `deal_type = '직거래'` |

60일 조건이 필요한 이유: 잔금·등기에 시간이 걸리므로 최근 거래에 등기일자가 없는 것은 정상이다.

### 3.8 표현 규칙 (화면 문구에 강제)

| 금지 | 사용 |
|------|------|
| "자전거래 의심" | "신고 후 해제된 거래" |
| "허위 신고" | "등기 미확인 (계약 후 191일 경과)" |
| "역전세 위험 단지" | "만기 도래 물량 N건, 당시 대비 차액 N원" |

모든 페이지에 출처(국토교통부 실거래가, 공공누리)와 **데이터 기준일**을 표기한다.
사실 적시 + 출처 명시는 방어 가능하지만, 단정 표현은 그렇지 않다.

## 4. 제품 표면

### 4.1 SEO — 점진 공개

**단지 페이지 2~3만 장을 한 번에 발행하면 역효과다.** 검색엔진은 자동 생성된 얇은 페이지의
대량 발행을 doorway page로 판정하고 **사이트 전체 품질 평가**를 낮춘다.

`confidence`가 여기서 두 번째 역할을 한다.

- **`confidence = LOW` 또는 산출 불가 → `noindex`**
- 거래가 쌓여 MEDIUM 이상이 되면 색인에 편입

즉 데이터 품질 지표가 곧 색인 게이트다.

### 4.2 키워드 전략

| 키워드 | 경쟁 | 판단 |
|--------|------|------|
| OO아파트 실거래가 | 포화 (호갱노노·아실) | 포기 |
| OO아파트 전세 | 포화 | 포기 |
| **OO아파트 전세 만기 / 역전세** | 거의 없음 | **목표** |
| **OO동 역전세 현황** | 거의 없음 | **목표** |

단지명 단독으로는 대형 서비스를 이길 수 없다. 페이지 제목에 우리 수식어를 결합한다:
`OO아파트 전세 만기·역전세 현황 (2026)`.

### 4.3 URL 구조

```
/역전세/{시도}/{시군구}
/단지/{id}-{slug}
```

**평형 단위로 URL을 쪼개지 않는다.** 페이지가 얇아져 색인에 불리하다.
평형별 데이터는 단지 페이지 안에서 표로 제공한다.

### 4.4 무료 / 유료 경계

원칙: **콘텐츠는 전부 무료, 타이밍과 목록화가 유료.**
페이월 뒤의 콘텐츠는 색인되지 않으며, 색인되지 않으면 유일한 판로인 인바운드가 성립하지 않는다.

| 구분 | 범위 |
|------|------|
| 무료 | 모든 단지 페이지, 현재 전세 시세, 만기 물량 총계, 최근 거래 목록, 신고가 검증 사실 |
| 유료 | ① 만기 3개월 전 알림 ② **갱신권 소진 건 목록** ③ 관심 지역 전체 만기 리포트 CSV |

중개사가 지불하는 대상은 정보 자체가 아니라 **남보다 먼저 받는 것과 목록 형태로 받는 것**이다.

> **이 표는 최종 목표 모델이며, 1차 출시에는 적용하지 않는다.**
> §4.5에 따라 1차에는 결제가 없으므로 위 유료 항목(주간 다이제스트 포함)을 **전부 무료로 제공한다.**
> 이는 누락이 아니라 의도된 것이다 — 유료 예정 기능을 먼저 무료로 써보게 해야
> 구독 신청 수가 지불 의사의 신호로 기능한다. 과금은 이 신호를 확인한 뒤 도입한다.

### 4.5 1차 출시에 결제·계정을 넣지 않는다

결제 연동(포트원/토스페이먼츠)은 사업자등록 포함 최소 2~3주이며, 주 5~10시간 기준
**약 한 달 반**이다. 지불 의사가 확인되지 않은 상태에서 쓰기에는 과도하다.

1차는 **무료 전면 공개 + 이메일 구독 폼**만 제공한다.
"지역 만기 리포트를 받아보시겠습니까"에 이메일이 몇 개 등록되는지가 유료화 가능성의 실제 신호다.

같은 이유로 **계정·로그인·소셜 OAuth를 만들지 않는다.** 이메일과 관심 지역만 받는다.

### 4.6 알림 — 주 1회 다이제스트

funapp의 `NotificationService` + `EmailNotifier` 패턴을 이식하되 **주기가 다르다.**
실거래 데이터는 1일 1회 갱신되고 지표가 월 단위이므로, 건건이 발송하면 스팸이 된다.

매주 월요일 08:00, 관심 지역당 1통에 다음을 담는다.

1. 3개월 내 만기 도래 단지·건수
2. 그중 **갱신권 소진 건수**
3. 역전세로 전환된 단지
4. 관심 단지의 신고 해제 거래

채널은 **이메일만.** 카카오 알림톡은 사업자등록과 템플릿 심사가 필요해 1차 범위 밖이다.

| 1 | 파서 | 정상 / NODATA(03) / 쿼터초과(22) / 깨진 XML 4종 픽스처. resultCode 판정이 정확한가 |
| 2 | 해시·업서트 | 같은 거래를 두 번 수집해도 행이 늘지 않는가. **`해제여부`만 바뀌면 기존 행이 갱신되는가** |
| 3 | 단지 정규화 | 아파트명 표기가 달라도 지번이 같으면 하나의 `complex`로 묶이는가 |
| 4 | 산식 | 만기월 산출(계약기간 정상/결측/형식오류), 순수전세 필터, **표본 부족 시 confidence가 LOW로 떨어지는가**, 폴백 계단 |
| 5 | 통합 | Testcontainers MySQL로 수집 → 집계 → 조회 전체 경로 |

2번과 4번이 가장 중요하다. 각각 §1.3과 §3.5의 핵심 결정을 고정하는 테스트다.
funapp의 `CrawlServiceTest` 패턴을 따른다.

## 6. 구현 순서

총 예산 60~100시간. 각 단계 종료 시 **동작하는 산출물**이 남도록 분할한다.

### 1단계 — 수집 파이프라인 (2~3주)

프로젝트 셋업, API 클라이언트, XML 파서, resultCode 처리, `deal_hash` upsert,
`ingest_log`, 재시도 정책. 서울 1개 구로 검증 후 전국 백필.

**산출물:** DB에 전국 실거래 원본 (전월세 36개월, 매매 24개월)

> **검증 게이트 — 2026-09-21 사전 실측으로 통과.**
> 표본 26,173건(6개 시군구 × 6개월) 기준 `contractTerm` 채움률 **95.6%**,
> 백필 대상 구간(최근 36개월)에서 95% 이상으로 안정적이다. 50% 기준을 크게 밑돈다.
> 계약년월별로도 93.6%~97.1%로 고르다.
>
> 전국 백필 완료 후 같은 지표를 전수로 재측정해 이 추정을 확인한다.
> 전수 결과가 50%를 넘으면(사전 실측과 배치되는 결과이므로 개연성은 낮다)
> 2단계 진입 전에 지표 설계를 재검토한다.

### 2단계 — 지표 집계 (2~3주)

`complex` 마스터 정규화, 만기월 산출, 역전세 갭, confidence 폴백 계단,
갱신권 소진 집계, `deal_flag` 판정, `snapshot_date` 기반 스냅샷 교체.

**산출물:** 집계 테이블 3종

### 3단계 — 공개 페이지 (2~3주)

Thymeleaf 단지·지역 페이지, sitemap 생성(파일당 5만 URL 분할), `noindex` 게이트,
출처·기준일 표기, 표현 규칙 적용.

**산출물:** 검색 색인 가능한 사이트 (이 시점에 공개 가능)

### 4단계 — 구독과 다이제스트 (1~2주)

이메일 구독 폼, 구독 확인, 수신거부, 주간 다이제스트 발송.

**산출물:** 수요 신호 수집 시작 (유료화 판단 근거)
